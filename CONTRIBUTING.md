# Contributing to Macksie

Welcome! You do not need to be a programmer to help Macksie grow. Our immediate focus is to establish the project documentation and define a small, useful [Commons prototype](commons/README.md).

This contribution guide describes the working review process for this repository. It does not finalize the [draft Accords](docs/ACCORDS.md), the Ten Foundations, or Macksie's governance.

## Find a way to help

| Who | Useful contributions now |
| --- | --- |
| **Developers** | Review the proposed entry model, identify the smallest technical requirements, compare implementation options with clear tradeoffs, and write acceptance scenarios. Application code belongs in a later, separately scoped change. |
| **Designers** | Sketch the entry, search, source, and revision-history views; improve navigation and language; review keyboard access, contrast, and screen-reader needs. Label mockups as proposals. |
| **Researchers** | Propose a small starter collection, trace claims to primary sources where possible, record provenance, identify conflicting evidence, and suggest a clear source-review process. |
| **Volunteers** | Improve documentation, check links, help newcomers, organize questions, review plain-language explanations, and propose translations or usability feedback. |

The [Foundry Glances](foundry/README.md) offer ways to coordinate these efforts. They are not prerequisites for participation or grants of access or authority.

## Before you start

1. Read the [project introduction](README.md), [roadmap](docs/ROADMAP.md), and the relevant component brief.
2. Check [existing issues](https://github.com/MacksieOS/macksie/issues) and [pull requests](https://github.com/MacksieOS/macksie/pulls) to avoid duplicating work.
3. For a substantial change, open an issue describing the problem, who it helps, the proposed scope, and unresolved questions. Small documentation fixes can go straight to a pull request.
4. Keep proposals clearly separate from approved decisions and implemented behavior. Explain which sources support factual claims.

## Make a reviewable contribution

1. Work on a feature branch, using a fork if you do not have repository write access. Do not edit the default branch directly.
2. Keep each change focused. For this foundation stage, contribute documentation and organization; propose application work separately.
3. Use readable Markdown, descriptive headings, and relative links between repository documents.
4. Open a pull request against `main` explaining the problem, the change, how you checked it, and any decisions still needed.
5. Respond to review. Leave the pull request open for maintainer review; do not enable automatic merging as part of this workflow.

## Before requesting review

- Check spelling, terminology, relative links, and Markdown rendering.
- Make sure every listed file and section exists, and every named Foundry Glance is spelled consistently.
- Keep proposed features distinct from working capabilities; do not imply the Commons prototype has already shipped.
- For research, provide source links, dates where relevant, and an explanation of uncertainty or conflicting evidence. A citation is a path to evidence, not a guarantee of correctness.
- Include only material you are permitted to share. Do not include credentials, private personal information, or copied material without appropriate permission.
- Describe checks actually performed. Documentation-only changes do not need invented application tests or build results.

## Discuss with care

Explain your reasoning, ask questions in good faith, and critique ideas without attacking people. Make room for different experience levels and accessibility needs. These are practical expectations for collaboration, not a substitute for the future Accords or an adopted code of conduct.

Use public issues for ordinary questions and non-sensitive concerns. Do not post exploit details, secrets, or private reports publicly; a confidential reporting route still needs to be established before public operation.

## Decisions still to make

License selection, contributor terms, formal governance procedures, and the authoritative Ten Foundations remain unresolved in this repository. Do not add a license, claim a contributor agreement exists, or turn draft policy into settled rules as part of an unrelated contribution. Raise these changes explicitly for review.
